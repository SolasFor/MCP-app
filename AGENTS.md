## Неподлежащие регрессии требования
1. Сохраняй Python, PyQt6, MCP SDK, SQLite, Windows 10/11, PyInstaller и Inno Setup, если для изменения стека нет отдельного решения владельца.
2. Сохраняй три существующих сценария OAuth: безопасный, белый список (по умолчанию для новой GUI-конфигурации), полный доступ. Полный доступ позволяет произвольные CMD/PowerShell/SSH-команды с правами текущей учётной записи. Не добавляй обязательных подтверждений каждой команды внутри MCP-app. Не обходи подтверждения самого AI-клиента, UAC, правила Antigravity или ОС. Не включай полный доступ автоматически.
3. Не показывай окна терминала при штатных командных вызовах. Запуск явно запрошенных GUI-программ остаётся возможным.
4. Сохраняй существующие инструменты, параметры, OAuth-клиентов и данные посредством совместимых миграций; не используй токены в URL. Не подменяй issuer/resource URL и не переиспользуй токены между несовместимыми контекстами.
5. Полный shell не является sandbox: отдельные разрешения инструментов и DPAPI не ограничивают произвольный код от имени того же пользователя. Не заявляй обратное. Для ограниченных клиентов обеспечивай fail-closed проверку прав на каждом вызове. Секреты не должны попадать в логи, коммиты, артефакты, вывод инструментов или окружение без необходимости.
6. Дизайн: Linear + Docker Desktop, Dark/Light/System, единая дизайн-система, русская и английская локализации. Главная сохраняет единый обзор и основные функции подключения; расширенная настройка провайдеров может иметь отдельную страницу.
7. Четыре публичных UI-провайдера: Cloudflare Quick, Cloudflare Named, ngrok и Tailscale Funnel. Local only — внутренний/совместимый режим, не возвращай удалённые из UI транспорты без запроса. Не отключай авторизацию из-за loopback или доверия к туннелю.
8. Не симулируй рабочий функционал в релизе и не используй фиктивные результаты тестов. Не маркируй недоступные проверки как пройденные.

## Автономный рабочий цикл
- Начни с git status и затронутых файлов; ветки, теги, CI, окружение и полный обзор проверяй по необходимости (обязательно для этапов ROADMAP и релизов). Не удаляй изменения владельца; при конфликте используй отдельный worktree/ветку или сообщи о нём.
- Для этапов ROADMAP сверяй готовность с PROGRESS.md и запускай baseline-тесты. Для локальных исправлений достаточно затронутых проверок; существующие ошибки отделяй от регрессий.
- Выполняй этапы по зависимостям ROADMAP, разбивая сложную работу на проверяемые задачи. Параллельная работа — только по правилам экономии контекста ниже.
- На каждый этап отдельная feature-ветка, при необходимости несколько PR. Пиши код, миграции, unit/integration/security-тесты, документацию; запускай проверки и проверяй реальные результаты. Исправляй ошибки, а не отключай проверки.
- Проверяй актуальные официальные API/CLI, протокол MCP, версии библиотек и лицензии до интеграции. Фиксируй зависимости и проверяй источники бинарников. Не выдумывай команды и параметры.
- Обновляй PROGRESS.md при изменении статуса ROADMAP, существенных результатов, блокеров или проверок; после этапа фиксируй коммиты, PR, CI и оставшиеся ручные тесты. Статусы: TODO, IN_PROGRESS, BLOCKED, VERIFIED, MERGED, RELEASED. VERIFIED требует доказательств.
- Продолжай следующие независимые задачи без лишних вопросов. Если нужны учётные данные, платный сервис, внешнее разрешение, лицензия, админ-права или физическая проверка, не выдумывай их и не обрабатывай их через открытые логи. Запиши BLOCKED, точную ручную операцию для владельца и продолжай всё незаблокированное. Не переходи через блокирующую зависимость.
- Если заканчивается контекст или лимит агента, зафиксируй текущее состояние и точную команду/действие для возобновления. Следующий сеанс начинает с AGENTS.md, ROADMAP.md и PROGRESS.md, а затем сверяет Git/CI.

## Экономия контекста и квоты AG
- Режим выбирает владелец: одна обычная модель или встроенный Orchestrator AG. Инструкции одинаковы. Без второго оркестратора, Swarm, Boost, Teamwork и самостоятельных субагентов по умолчанию. Для небольших исправлений: точечное чтение, минимальный патч, целевые тесты, краткий отчёт. Не запускай полный цикл ROADMAP для каждой мелкой задачи.
- Swarm и субагенты — только по явному запросу владельца или с его отдельным согласованием. Разделяй независимые области, не допускай одновременного редактирования одних файлов; главный агент отвечает за интеграцию.
- Используй Skills и MCP только по задаче: один основной Skill, дополнительные — если без них не хватает конкретной экспертизы. Не загружай все инструкции и не дублируй рабочие процессы.
- Ponytail Lite — для обычных правок; Superpowers — для сложной отладки, архитектуры или существенных изменений. Не жертвуй OAuth, проверками прав, обработкой ошибок и обязательными тестами ради сокращения кода.
- Для UI источники истины — DESIGN.md и существующие токены/компоненты PyQt6. UI/UX Pro Max или Impeccable — для UX, Emil Design Eng или Apple Design — при необходимости для взаимодействий, Break UI — для проверки крайних данных; не применяй весь набор сразу. Не переноси CSS/React-паттерны в Qt буквально.
- Предпочитай локальные Git, поиск, Ruff и unittest, если они достаточны; Context7 — для неизвестных API, Cloudflare/Chrome DevTools/SonarQube — по профилю задачи. Ограничивай вывод логов, не повторяй успешные проверки без причины; не сокращай обязательные проверки безопасности и релиза.

## Полный аудит после v1.0.0
- Для полного аудита используй проектный Skill mcp-app-audit (.agents/skills/mcp-app-audit/SKILL.md). Обязательный план и критерии приёмки — docs/maintenance-audit.md. Начинай с P0: запуск и ACL Windows, затем безопасность, MCP, хранилища, UI, сборка и документация. Не исправляй неподтверждённые предположения.
- ACL: определяй пользователя по SID токена процесса; не разрешай короткий USERNAME, не снимай наследование до гарантированного предоставления прав, не добавляй Everyone. Не меняй ACL реальных данных рекурсивно автоматически. Не удаляй vault, ключи DPAPI или базы для устранения ошибки. Проверяй временные профили, сохранение данных при обновлении и обычный запуск без администратора.
- При системном отказе доступа не запускай сетевой сервер в небезопасном состоянии; покажи понятное сообщение и путь к диагностике. Проверяй startup отдельно от selftest.
- Ревьюируй изменение перед интеграцией. Для P0/P1 обязательны негативные тесты и реальные доказательства; пропуски и недоступные среды маркируй NOT_RUN/BLOCKED.

## GitHub и релизы
- Разрешено создавать feature-ветки, локальные коммиты, пушить свои ветки и открывать PR при наличии доступа. Не делай force push, reset --hard по пользовательским изменениям, удаление чужих веток или прямой push в main. Не изменяй права репозитория или branch protection.
- По умолчанию merge в main, публикация публичного релиза и развёртывание внешних сервисов требуют согласия владельца. Если владелец отдельно разрешил автоматические merge/release, соблюдай CI, обязательные reviews и критерии приёмки; не обходи защиту ветки. Не публикуй этап как завершённый при незакрытых обязательных проверках.
- До релиза: unit/integration/security checks, Windows build, EXE selftest, установка/обновление в тестовом окружении, SHA-256, SBOM, release notes. Для реальных внешних интеграций требуется live smoke test; мок не заменяет его. Не подписывай сборки фиктивным сертификатом и не устанавливай неподписанные автообновления.
- Не расходуй средства, не создавай платные подписки, не публикуй новые публичные маршруты к компьютеру и не изменяй реальные DNS/ACL без отдельного разрешения владельца. Разработка и мок-тесты этих функций разрешены.

## Формат итогового отчёта
Для каждого этапа: реализовано; изменённые модули; тесты (команды, результаты, ссылки CI); миграции; ограничения и риски; PR/коммит/версия; незавершённые проверки; следующий шаг. Не говори «готово», если обязательная часть не проверена. Итоговая цель — работающий продукт, не отчёт сам по себе.

## Graphify — локальная навигация по архитектуре

- Graphify — вспомогательный индекс исходного кода, не источник истины. Для широких архитектурных вопросов, поиска связей и оценки влияния изменений сначала используй graphify query, path или explain при наличии актуального graphify-out/graph.json; для точечных правок прямой поиск может быть дешевле.
- Сверяй значимые связи, выводы безопасности и изменения с реальным кодом и тестами. Не подменяй графом review OAuth, ACL, DPAPI и разрешений.
- Используй только локальный AST-режим: graphify update . из корня текущего worktree. Обновляй индекс после значимого набора изменений или смены ветки, не после каждого файла; при отсутствии CLI продолжай обычным поиском. Не запускай watcher, Git hooks, дополнительные MCP, cloud sync, семантические API/LLM-индексацию и субагентов без отдельного разрешения.
- Соблюдай .graphifyignore и .gitignore. Не индексируй реальные секреты, пользовательские каталоги, токены, журналы, базы, сборки, окружения и внешние пути; не публикуй graphify-out. Перед индексацией убедись, что worktree не содержит непредусмотренных reparse points.
- Graphify для навигации, Ponytail Lite для минимальных исправлений, Superpowers для сложной отладки. Граф не отменяет тесты и ограничения безопасности. Инструкции AGENTS.md имеют приоритет над общими правилами Graphify.

## Следующий цикл: обязательные решения владельца
- N00 — только подготовка; не начинать код новых функций до отдельной команды владельца. Затем выполнять N01–N13 по зависимостям, по одному этапу с отдельными коммитами и проверками. Перед каждым этапом показать план и отметить фактический baseline.
- Отдельная вкладка «Серверы» исчезает только после доступности всех существующих профилей в Workspaces; backend и MCP API сохраняются. Миграция обратимая, без потери данных или повышения прав.
- Не развивать резервное копирование; сохранить существующую функцию и технический rollback. Безопасное автообновление не равно разрешению установить неподписанный пакет. Доверие к подписи должно быть независимым от скачанного артефакта.
- Не изменять глобальные настройки Antigravity, разрешения, токены, sidecars, DNS, SSH-службы и ключи владельца ради прохождения тестов. Режимы использования инструментов — docs/antigravity-workflow.md.
- Сначала точечные проверки, затем полный gate на значимых границах. Нельзя объявлять VERIFIED без доказательств; независимое ревью ChatGPT/владельца перед merge/release.

## Обязательный production gate после merge N02
N02 MERGED (PR #38, 4b9bedb) означает приёмку кода, не допуск автоустановки. PRODUCTION_TRUST_ROOTS и PRODUCTION_PUBLISHER_THUMBPRINTS остаются пустыми до отдельного решения владельца; production auto-install и автоматический boot-recovery BLOCKED (MISSING_TRUST_ROOTS), installed без криптографически проверенного rollback — BLOCKED (NO_ROLLBACK_CONTRACT). До включения production требуется отдельная приёмка инфраструктуры Ed25519/Authenticode, проверка криптографической целостности именно восстанавливаемого portable-пакета до запуска его бинарника, проверка rollback при прерывании и потере питания (включая отсутствие install_dir между rename). Самопроверка/health не заменяют криптографическую проверку. Первый переход с неподписанной 1.0.2 — вручную в доверенную сборку. Не включать production-ключи/автоустановку в N03–N13 без отдельной авторизации и успешной приёмки этих gates; не выдавать BLOCKED/NOT_RUN за PASS.
