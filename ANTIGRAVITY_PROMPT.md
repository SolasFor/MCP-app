## 1. Сценарии мастера
1) Выбор конкретной папки или обнаружение проектов только в явно выбранном родительском каталоге. Не сканировать весь диск, home, сеть, внешние устройства. Ограничить глубину, число записей, размер файла, время, суммарный объём и поддержать отмену; исключить node_modules, .git, .venv, build/dist/cache, секретные и reparse/symlink каталоги.
2) Статический read-only анализ и показ обнаруженного стека, корня, источников сведений, уверенности и предупреждений.
3) Предложить название, уникальный ID, root, runtime/venv, команды test/build/run, возможные server profiles и их связи. Все предложения редактируемы и помечены как предложения, не как проверенная работоспособность.
4) Предпросмотр точного набора изменений и разрешений, выбор нужных команд и серверов. Никаких автоматически включённых privileged permissions/autostart/hooks.
5) Явное подтверждение создания; после commit показать Workspace в существующем списке. Не запускать проект при создании. Отдельное действие владельца для исполнения после просмотра точной команды и необходимых разрешений.

## 2. Read-only discovery и поддерживаемые проекты
Переиспользовать canonical_workspace_root и безопасное открытие файлов с проверкой реального handle/пути. Для каждого читаемого файла проверять границы выбранного корня, каждый сегмент, symlink/junction/reparse/ADS/device/UNC, regular file, размер, race; не читать FIFO/устройства. Отклонять traversal, абсолютные ссылки вне root, внешние include и конфиги. Не ослаблять существующий path_security. Git: только безопасные признаки наличия репозитория/корня, не запускать git hooks и не читать .git/config или объекты; внешние gitdir/worktree отметить как непроверенные. Не подниматься выше выбранной границы поиска без явного согласия. Не запускать даже python/node/npm/git/docker --version из проекта; обнаружение runtime только по безопасным метаданным/доверенному системному поиску, не исполнять найденный файл.
Python: pyproject.toml через tomllib, requirements/lock как ограниченные текстовые метаданные без install и без раскрытия URL credentials, venv по структуре, pytest/unittest, статически объявленные scripts/entrypoints, framework signals. Не импортировать Python, setup.py, plugins, conftest или project modules.
Node/TS/Next.js: package.json, lockfile presence, packageManager, scripts, dependencies/framework signals, workspaces, tsconfig presence. Не исполнять JS config, npm/pnpm/yarn/npx, lifecycle scripts. Предлагать точные команды из доказуемых scripts с видимым источником, не угадывать dev/build/test.
Docker Compose: безопасный статический YAML parser (если уже доступен или обоснованная pinned dependency с license/security gate), bounded nodes/depth/aliases, reject tags/unsafe construction, duplicate keys и внешние include/extends; не выполнять docker compose config/up/pull/build, не раскрывать env_file/environment values, не разворачивать переменные, не читать .env. Если parser не поддерживает безопасный режим — presence-only + явное ограничение.
Monorepo/mixed stack: ограниченный анализ workspace declarations (без выхода из корня, recursive glob explosion), выбор корневого проекта или конкретного подпроекта, не плодить дубликаты. Неизвестный/пустой/неоднозначный проект: ручной режим, честное «не определено». Невалидные/огромные/нечитаемые manifest — диагностировать, без автоматических команд из догадок.
Порты/entrypoints: только статические литералы и явно объявленные настройки, отличать предполагаемый порт от проверенного; не сканировать сеть, не запускать probes. Не искать токены, SSH keys, .env*, credentials, сертификаты, секретные файлы; не импортировать значения секретов или отправлять исходники/manifest наружу. Вывод и логи редактировать; не показывать env/URL credentials или произвольные строки со встроенными секретами. Команды с подозрительными секретами не предлагать автоматически.

## 3. Сохранение, права и безопасное исполнение
По умолчанию новый Workspace read-only (read=true, write/delete/execute/git=false), без автоматического доступа существующих OAuth-клиентов: проверить реальную семантику allowed_clients/min_profile/overrides (пустой список может означать всех); не выдавать пустой список за deny-all. Если модель не умеет исключить клиентов по умолчанию, минимально расширить её с обратно совместимым поведением старых профилей и тестами. Явно показывать effective permissions; доступ и execute только при подтверждении владельца. Не менять Safe/Allowlist/Full Access и существующие клиентские права. Не расширять scope при создании/связях.
Серверные предложения через существующий ServerProfile/ServerConfigStore/WorkspaceServerCoordinator: новые профили workspace_scoped, autostart=false, без секретов и без автоматического запуска; существующие профили не менять и не связывать по одному совпадению cwd/имени. Привязка существующего — отдельный явный выбор, не расширяющий права. Использовать N03 transaction/lock hierarchy, согласованный атомарный commit workspace+servers+links; crash/ENOSPC/access denied не оставляют частичных записей, duplicate profiles или orphan links. При конфликте повторный preview, не overwrite. Проверить повторное подтверждение, stale plan, path swap/TOCTOU, ID/root aliases/case insensitive Windows, вложенные проекты (явно показать различие, не запрещать легитимный monorepo). Cancel/back/close до commit не записывают пользовательские данные. Не расширять BackupManager.
Запуск через существующие TaskManager и ServerManager / защищённый Local Admin API, не напрямую из wizard. Перед исполнением проверять актуальные permissions/approval/emergency stop, актуальные root/cwd/argv и изменившийся manifest/command: не исполнять подменённую конфигурацию незаметно. Учитывать shell syntax, Windows quoting, lifecycle hooks: не обещать sandbox; даже npm run может выполнить pre/post hooks при явном запуске. Никаких новых обходов проверки безопасности, автоматической установки зависимостей или подтверждений для обычных действий уже авторизованного Full Access.
