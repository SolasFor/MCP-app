## 1. UX и способы добавления
В существующей вкладке «Устройства» компактный мастер: (1) адрес/источник, (2) проверка TCP и host key, (3) метод аутентификации и тест, (4) определение ОС/возможностей, (5) права и итоговый preview, (6) явное сохранение. Можно объединить соседние шаги без потери границ безопасности. Сохранить ручную форму и редактирование существующих профилей. Показать, что удалённому устройству не нужен MCP App, если доступен SSH; SSH отличается от самостоятельного MCP endpoint/Gateway, не объединять их архитектурно. Не требовать Cloudflare или Tailscale для обычного SSH.
Ручной адрес: hostname/IP IPv4/IPv6, порт, пользователь, имя/группа; валидировать через существующий DeviceProfile/validate_host, нормализовать корректно DNS/IPv6/нестандартный порт, не интерпретировать как URL/shell. Не принимать NUL/CRLF/option injection, неоднозначные адреса, proxy/jump без реализованного безопасного контракта. Явный Test, состояние неизвестно/недоступно/не доверен/аутентификация не удалась/успех, ошибки по фазам, без ложных успешных статусов.
Импорт SSH Config: только явно выбранные конкретные Host из ~/.ssh/config либо указанного файла, read-only, bounded размер/строки; использовать/укрепить существующий import_ssh_config. Preview каждого Host, не выполнять Match exec, ProxyCommand, LocalCommand, RemoteCommand, Include или неизвестные директивы, не следовать wildcard/negation/сложным правилам с неоднозначной семантикой; диагностировать unsupported и предложить ручную настройку. Не читать приватные ключи при импорте; IdentityFile — только путь, безопасное разрешение без выполнения/произвольного чтения. Не импортировать пароли, разрешения или trust из комментариев. Не изменять ~/.ssh/config или global known_hosts. Повторный импорт не дублирует и не перезаписывает существующий профиль.
Опциональное обнаружение: по умолчанию OFF. Только после отдельного явного согласия на конкретный CIDR/ограниченный список адресов доверенной сети и порт(ы), с показом границ, максимума хостов, времени и отмены; ограниченный TCP SSH probe без перебора логинов, паролей, ключей, баннеров за пределами согласованного scope. Никакого полного скана LAN/интернета, автоматического поиска всех интерфейсов/VPN, обхода сегментов, DNS rebinding/выхода за выбранный диапазон. Умеренные hard caps, bounded concurrency/rate/time, закрытие сокетов, cancellation, не сканировать широкие IPv6/IPv4 диапазоны. Tailscale только при наличии доверенного локального CLI, явном согласии на чтение локального status --json, ограничить размер/timeout, показать доступные peers и выбрать конкретного; не вызывать login/up, не менять ACL/routes, не отправлять данные наружу. Если нет CLI/доступа — понятный NOT_AVAILABLE и ручной режим. Обнаружение не равно доверие/успешная аутентификация.

## 2. Host key — обязательная граница доверия
Сохранять strict_host_key=True и RejectPolicy во всех runtime entrypoints, включая legacy oauth_ssh_command, SFTP, metrics, service, task/reconnect. Никакого AutoAddPolicy, WarningPolicy, accept-all, безусловного TOFU и отключения проверки. Существующий корректный known_hosts поддержать, включая hashed entries, host aliases и [host]:port; не угадывать доверие для другого имени/порта. Unknown host: ограниченный pre-auth SSH handshake только с согласованным endpoint, извлечь алгоритм и SHA256 fingerprint публичного host key, показать точное имя/порт, без пароля/agent signatures/private-key auth до подтверждённой проверки. Требовать независимую сверку с ожидаемым fingerprint, полученным владельцем по доверенному каналу (локальная консоль целевого устройства/администратор); одно лишь ssh-keyscan или «принять увиденный ключ» не доказательство. Изменённый ключ — hard fail, не перезаписывать и не предлагать тихий обход. Отдельный явно подтверждённый workflow ротации с независимой сверкой и предупреждением, если нужен; иначе документировать ручную процедуру. При изменении адреса/порта/username/auth/trust или ключа инвалидировать результаты теста.
Привязать проверку к точному host/port/key algorithm/key bytes, endpoint и snapshot. На следующем подключении и перед использованием credentials сверить фактический negotiated key с утверждённым; не полагаться на старый TCP probe или fingerprint из GUI. Запрет downgrade/неожиданного fallback к другому ключу. Проверка действует в момент аутентификации; тесты race между probe и auth/save/reconnect. Не хранить открытые секреты в trust storage. Для новых записей предпочтительно существующая модель known_hosts_path с отдельным app-managed known_hosts (ACL, атомарность, проверка symlink/reparse); не редактировать системный файл без отдельного согласия. Если существующий known_hosts используется как источник доверия, сохранять pin/контракт так, чтобы его подмена не расширила доверие незаметно. Не ломать существующие профили и корректные legacy known_hosts; документировать различие старого и нового контракта. Cancel до сохранения не меняет trust store.

## 3. Аутентификация, диагностика и инструкции
Поддержать agent, выбранный существующий private key (при необходимости passphrase), password через SecretStore ref; не переключаться скрытно между методами, не пробовать все agent keys/пароли без согласия, не передавать secrets в command line, URI, логи, exceptions, telemetry, stdout, clipboard, TaskSpec или JSON. Явно проверить параметры Paramiko allow_agent/look_for_keys/password/key_filename/passphrase для каждого метода; безопасная обработка ошибки чтения/парсинга ключа, encrypted key, wrong password, unavailable agent. Секреты теста только в памяти минимально необходимое время, очистить UI/refs при отмене; записывать DPAPI/SecretStore("ssh") только после явного сохранения. Не создавать plaintext fallback, не читать чужие ключи. Не обещать гарантированное стирание Python memory.
Опционально генерировать ключ только по отдельному явному действию, с безопасным алгоритмом, выбранным местом, ACL, исключительным созданием без overwrite, passphrase через безопасный UI, показывать/копировать только public key. Не загружать private key на удалённое устройство и не менять authorized_keys автоматически. Отмена не удаляет ранее существовавшие файлы. Если безопасная генерация недоступна — показать инструкции, не реализовывать сомнительный fallback.
После host-key verification и успешной auth отдельный согласованный ограниченный read-only probe: определение Windows/Linux/unknown и только необходимых возможностей SSH/SFTP (без доступа к содержимому пользовательских файлов), фиксированные безопасные команды, bounded timeout/output, no shell interpolation, no sudo/UAC. Не создавать каталоги/файлы на remote при тесте, не устанавливать агенты, не менять службы/sshd/firewall/registry, не запускать пользовательские команды. Проба доступности capability не означает предоставление права. Не считать unknown OS Linux; показывать неизвестное, не обещать работу N10. Уважать emergency stop и запреты на сетевые операции, где применимо. Закрывать transport/channel/sftp/sockets при всех исходах, включая cancel, timeout, auth failure, закрытие GUI. Не оставлять background worker/process, игнорировать stale results при смене endpoint.
Контекстные инструкции Windows 10/11 (OpenSSH Server, sshd, firewall, public key/known_hosts) и Linux (OpenSSH Server, distro-specific различия) с безопасным ручным выполнением владельцем на целевом хосте. Проверить по официальным источникам. Не включать sshd, firewall, парольную аутентификацию, root login или sudo автоматически. Указать, что SSH обычно работает в LAN/VPN; не рекомендовать публикацию 22 порта в интернет как обязательную. Отдельно описать Tailscale/обычный SSH и независимый MCP App.

## 4. Права, сохранение и совместимость
Новые/импортированные профили deny-by-default: все DevicePermissions false (execute, sftp_read/write, service_control, metrics, docker_read), никакого автоматического доступа OAuth даже при пустом allowed_clients. Изучи реальный _authorize/list/info/health, legacy и task restart/reconnect, пустой список может означать всех. Если нужен новый флаг allow_oauth_clients, обратно совместимый default при чтении старых профилей (сохранить их права), false для новых мастера/ручной формы/import; строго валидировать типы, не ослаблять malformed/corrupt config. Отдельное явное действие владельца для grants, показывать effective permissions: глобальный OAuth профиль + device scope + capability + allowed_commands/services/sftp roots/quota. Safe полностью блокирует удалённые устройства; Allowlist сохраняет текущие точные разрешения, Full Access без искусственного sandbox для явно разрешённого устройства, существующие deny gates не обходить. Не добавлять подтверждение каждой обычной разрешённой команды Full Access. Не расширять права при импорте, редактировании, повторном тесте, смене host key. Не обойти через device_info/health, legacy oauth_ssh_command, direct MCP, Automation, TaskManager, SFTP, service или reconnect. Не смешивать owner GUI и OAuth. Актуальные права/revoke/emergency stop перед dispatch, не доверять старому preview.
Сохранять существующие device IDs, host/user, known_hosts, secret refs, токены, OAuth grants, allowed_commands/services/roots, quotas, job history. Не переносить автоматически secrets между endpoints. Проверить duplicate IDs/casefold, canonical host/port/user aliases, не объединять разные SSH accounts/hosts без явного выбора. Не перезаписывать existing profile при совпадении; edit только явный. Preview точных данных/разрешений/host key/auth method (без значений secrets), fingerprint плана, freshness test и stale plan rejection: изменение endpoint, trust, creds, registry/permissions после preview требует повторной проверки. Атомарный commit DeviceStore+app-managed known_hosts+новые SecretStore refs, единый lock order, fault injection (ENOSPC, PermissionError, crash, concurrency), old secret сохранён до durable commit, rollback/recovery fail-closed без изменения чужих файлов. Переиспользовать существующие atomic_io/N03 patterns без нового BackupManager. Cancel/back/close до commit не записывают конфиг/trust/secret; исключение — отдельно явно запрошенная генерация ключа с понятным результатом. Не автоматически подключаться/запускать задачи после сохранения.
